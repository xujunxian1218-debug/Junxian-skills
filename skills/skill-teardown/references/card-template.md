# 分析卡模板（九段填写规范）

> skill-teardown 的输出模板。第 3 步逐段产出时按本文件写卡。
> 四条通用规则贯穿全卡：①输入缺失的项标「未提供」，不允许编造；②不确定的判断用标注协议标出；③材料撑不起的段落写「材料不足」而非硬编；④跨稿 / 跨卡引用统一「源稿名 + 节号」命名空间——保留被引稿内部节号不改写，整合成稿零改稿嵌入，防整合时引用漂移。

## 卡片骨架

```markdown
# {Skill 名} 分析卡

## 1. 元信息
## 2. 总体分析
## 3. 道：顶层原则
## 4. 法：流程框架
## 5. 术：可复用资产
## 6. 例：好例子 / 坏例子
## 7. 戒：边界与风险
## 8. 洞察（分析者判断，与原文严格区分）
## 9. 版本记录
```

**快扫版骨架**（快扫深度用）：元信息（精简为核心字段）+ 总体分析 + 道层要点 3-5 条 + 一句话判断（值不值得引入/深究，理由一句话）。

## 第 1 段 · 元信息

**核心字段（默认必填，11 项）：**

| 字段 | 填写规范 |
|---|---|
| 来源链接 | 公开链接填 URL；社群 / 私有渠道填渠道名。不允许编造 URL |
| 分析时间 | YYYY-MM-DD |
| 版本基准 | Skill 自身版本号及来源；无版本管理必须标注「无版本管理」 |
| 实际读取的文件清单 | 见下方读取标注规范 |
| Skill 类型 | 从类型三组中选，可多标签 |
| 主领域 / 主场景 | 一句话 |
| 标签 | 关键词 |
| 分析深度 | 快扫 / 标准 / 深度 |
| 分类置信度 | 高 / 中 / 低——对类型判别没把握就标出来，这是诚实信号不是弱点 |
| 上下游 Skill 关系 | 见下方 5 种填法 |
| evals 覆盖度 | 有 evals 时标「类型 + 数量 + 覆盖场景概述」；无则标「无 evals」 |

**条件字段（4 项，命中触发条件才填）：** 分发形态 / 变体关系 / 所属生态 / 素材域清单——前三项触发判定见 references/analysis-angles.md；**素材域清单**触发条件 = 批量拆解或同家族多版本素材：填委托方提供的同域 Skill / 版本清单，逐项标注「本包独有 / 跨包共享」；委托方未提供时，卡内凡对「其他 Skill / 其他版本是否存在」的断言一律标 [分析补充]，不当作材料事实。

**文件读取标注规范：**

| 情形 | 标注方式 |
|---|---|
| 完整读取 | 全文逐行读取（默认，无需特别标注） |
| 部分读取 | 标「部分逐行读取」+ 读取范围（前 N 行 / 关键函数 / 特定章节），其余经 SKILL.md 或其他文件的描述理解 |
| 完全未读取 | 标「完全未读取（原因）+ 经 X 描述理解 + 理解范围」——与部分读取严格区分：该文件内容零原始核对 |

**Skill 类型三组（11 种，多标签）：**

| 组 | 类型 | 辨析 |
|---|---|---|
| 业务产出层 | 文档链型 / 创作型 / 商业估算型 | 文档链型产出链条交接文档；创作型产出终端内容；商业估算型产出结构化估算 |
| 执行协作层 | 工程实现型 / 对话编排型 / 编排型 / 多代理协作型 | 工程实现型靠脚本与契约；对话编排型是面向用户的多轮对话收敛；编排型是 skill 级路由（委托其他 skill）；多代理协作型是子代理级调度。编排型与多代理协作型可共存于同一 Skill |
| 方法元层 | 方法论型 / 协议型 / 横切型 / 元管理型 | 方法论型是思维上位 / 泛化；协议型无脚本纯纪律；横切型可叠加在任意环节；元管理型的分析对象是 Skill 本身 |

**上下游 Skill 关系（5 种填法，按被分析 Skill 在链条中的角色选）：**

| 方式 | 适用 | 填法 |
|---|---|---|
| 链式型（默认） | 属于某条产出链条 | 上游产出 → 本 Skill → 下游消费，记录上下游 Skill 名；硬编码的 Skill 名必须显式记录（这是断链风险的识别点） |
| 横切型 | 可叠加在任意环节（质量保障 / 日志 / 输出风格类） | 标「独立（横切）」+ 横切定位与叠加方式，不强行归链 |
| 跨体系映射型 | 硬编码的下游名可能与其他体系的 Skill 对应同一范式段 | 范式结构 + 硬编码下游名 + 可能映射。**必须标注为推断** |
| 方法论上位 / 特化型 | 是另一 Skill 的领域无关上位（或反之特化） | 标「独立（方法论层）」+ 上位 / 特化关系。**必须标注为推断**，除非原文明示。与跨体系映射的区别：映射是「同一范式不同命名」，上位 / 特化是「抽象程度不同」 |
| 孤立型 | 无已知上下游 | 标「孤立」+ 注明是材料不足以判断，还是判断确实孤立 |

## 第 2 段 · 总体分析

≤150 字。一句话定位 + 这个 Skill 最值得学的 1-2 个点。标准：读者 10 秒内能判断是否值得往下读。

## 第 3 段 · 道：顶层原则

- 提炼 2-5 条核心原则，必须写成**判断句**，能解释流程为什么这样设计
- ❌ 禁止空话：「注重质量」「保持专业」
- ✅ 正确示例：「当最终需要协作编辑时，可编辑性优先于视觉炫技」
- 关键判断句后尽量附原文短引佐证
- **版本交付维度**：多版本 / 多阶段交付的 Skill 必须提炼「为什么要分版本」的判断句；单版本交付标「单版本，无需分阶段」即可

## 第 4 段 · 法：流程框架

- 用 Mermaid flowchart 呈现，必须包含**六要素**：前置条件、决策节点、分支路径（有分支必须画）、回退机制、质量检查点、结束条件
- 先做形态判别（5 形态，见 references/mermaid-guide.md），按形态的图式要求画——不同形态的画法不可互换
- 图后附**流程要素对照表**，逐要素说明
- 若 Skill 无显式流程（纯协议型），画其认知流程（规则如何在每轮对话中生效）并标注这是推导

## 第 5 段 · 术：可复用资产

优先沉淀（有哪项写哪项），要求**拿走就能用**，不写抽象描述：

| 资产类型 | 说明 |
|---|---|
| 提示词结构 / 关键话术 | 尽量引用原文 |
| 输入字段定义 | 字段名 + 类型 + 约束 |
| 输出模板 | 模板本体 |
| 检查清单 | 「法」中每个质量 gate 必须在此对应落地 |
| 决策表 | 必须含条件列、动作列，如有优先级列 |
| 接口 / 契约定义 | CLI 参数表、JSON schema、状态文件格式、模型配置表、环境变量表等 |
| evals | 数量、覆盖场景、用例设计要点（如触发用例的正负例结构、断言的区分度） |
| 多平台适配配置 | 各平台配置路径、安装位置、适配差异；单平台省略 |
| 原创示范样本 | 必须标注「只示范 X 关系，内容均为虚构，不能拿去冒充事实」 |
| 命名规范 / 文件组织方式 | 目录约定、命名模式 |

**自由度档位（每项资产标注其一）**：高 = 文字原则（参照改写、适配自己场景后用）/ 中 = 参数化模板（改参数即用）/ 低 = 照抄资产（原样搬运即可用）——与资产类型列互补，复用者按档位一眼判断「怎么拿走」。

**质量 gate 三类**（检查清单资产必须覆盖三类）：

1. **流程确认点**：拦截推进的确认动作（用户确认门、模式判断 gate）
2. **产物验收点**：交付物的结构完整性检查。含**产物可见性**约束：禁止展示中间态（如未过验证的草稿不可见）/ 标注展示（checkpoint 显式区分）/ 自由展示
3. **信息深度自检**：不仅查「有没有回答」，还查「够不够具体」——只有形容词 / 模糊词不算过门，必须有具体数字、系统名、数据规模、时限等

**无 gate 空标（官方条款）**：被拆 Skill 全文无任何质量 gate 时，检查清单资产写「原文未设任何质量 gate」+ 一句话影响（哪些环节因此无拦截），不自创分类格式、不把非 gate 的普通步骤包装成 gate。

**执行者标注**（每道 gate 标由谁执行）：

| 执行者 | 标注要求 |
|---|---|
| AI 自评 | 必须注明「AI 自评，存在自我感觉良好风险」 |
| 自写脚本 | 注明可控可版本化（如 validate.py） |
| 外部标准工具 | 必须补「版本锚定状态」——浮动拉最新版（如 npx 直接跑）有不可复现风险 |

**缓解机制标注**（对每道 AI 自评 gate）：标注是否存在外部校验缓解，五类——①运行时机器脚本兜底；②开发时单元测试；③evals 人工对照；④evals 自动化盲评；⑤异上下文子代理审查。无任何外部校验时标「无外部校验，纯自评」。建议在检查清单资产中加「执行者 / 缓解」列。

## 第 6 段 · 例：好例子 / 坏例子（必填）

- 每个例子标注来源：[原文明示] / [约束推导] / [分析补充]
- 好例子：说明它符合什么原则；坏例子：说明它违反什么原则，要具体到行为
- 原文没有例子时，基于理解补充并标 [分析补充]，禁止伪装成原文观点

## 第 7 段 · 戒：边界与风险

三类归组，**每类过无问题下限**（各至少 2 条具体发现，或明确说明为何判断无此类问题）：

**适用边界类：** 不适合的场景 / 依赖的前提条件 / 容易诱导的错误用法 / 与同类 Skill 的潜在冲突。

**依赖与安全类：**

- **外部依赖链（必填）**：列出运行所依赖的所有外部文件、工具、技能、目录结构，标注缺失时的影响。无外部依赖标「无外部依赖」。协议型 Skill（无脚本无 references，核心资产是协议）标「协议型，无外部工具依赖」并说明这是固有特征而非信息缺失
- **外部依赖安全模型（条件：消费外部数据源时）**：四要素——信任级别声明（是否标注外部数据为不可信参考）/ 净化规则 / 版本固定机制（固定 commit SHA 而非分支名）/ 同步校验。无外部数据依赖标「无外部数据依赖」

**一致性类（数据源一致性校验）：**

1. **多独立数据源值不一致**：多个数据源（人读 md + 机读 json + 脚本硬编码）的值应一致但不一致，标注影响；含版本号在全文件中的一致性
2. **人读 / 机读双形态**：同一数据的两种表达，逐项比对要素一致性，标注「语义一致但表述粒度不同」的轻微差异，提示「只更新一处会漂移」
3. **规则口径一致性**：同一 Skill 内多处表述同一规则 / 承诺 / 枚举时的口径是否一致（典型：正文承诺某字段但输出模板无该列；同一枚举两处用词不同）。严重度三级：**表述漂移**（同一规则不同表述）→ **规则互斥**（多文件规则冲突，修正循环无法收敛）→ **审查缺口**（自检清单只查规范的子集）
4. **共享文档与定义演进同步性**（条件）/ **入口路由覆盖度**（条件）/ **复制式共享漂移**（条件）——见 analysis-angles.md

单一数据源且无多处规则表述时标「单一数据源，无一致性风险」。

## 第 8 段 · 洞察（与原文严格区分）

**基础四问（默认全答）：**

1. 这个 Skill 真正厉害的地方
2. 没明说但实际依赖的隐含判断
3. 可迁移到哪些其他场景
4. 可能过时或不稳的地方

**核心角度（默认）：**

- **AI 偷懒倾向纠正**：它纠正了 AI 哪些偷懒倾向（只写 happy path / 跳过边界 / 文案与字段混淆 / 攒到最后一起输出 / 停在中间交半成品等），独立编号列表；无则标「无显式反偷懒设计」
- **自评 gate 客观性风险**：AI 自评 gate 的客观性风险（占位符也算具体 / 自我评价偏松）；有交叉校核说明如何缓解；纯自评标「暂无外部校验机制」；全机器 gate 标「无自评 gate，客观性风险低」

**条件角度（8 项）**：触发判定见 references/analysis-angles.md。

## 第 9 段 · 版本记录

- 分析基准：日期 + 材料快照状态（哪些文件、什么版本）
- 后续是否需要重分析及触发条件，例如：Skill 大版本升级 / 流程结构变更 / 新增 evals / 收到此前缺失的配套文件 / 硬编码依赖的生态设施发生变更

**历史卡对照（条件：存在旧版分析卡时）**

- 对照注记 ≤200 字，计数口径统一为：**去空格总字符、不含标注头**
- 卡内引用的统计数字（行数 / 条数 / 差值等）随注统计口径与得出方式；与预置数字或旧卡数字比对不一致时，先按常见口径（净行数 / ±行数 / diff 总行数 / 字符数）穷举复算再下「不符」结论——数字对照宜多口径并列记账（如 ±行数 / diff 总行数 / hunk 数三列），从源头消除口径混用型假不符
- 对照中发现原 Skill 的示例被改写时，核验改写后的新示例仍满足该 Skill 自身明文规则——防「改例改掉正例」（被洗掉的恰好是原文规则的合规示范）
- 旧卡素材断链处补齐核验（旧卡引用但本快照缺失的文件，逐项标注补齐与否）
- 回审建议按三档标准写法给结论，粒度不得混用：
  - **条目级**：「建议回审第 X 章 Y 条目」——核心判断一致，个别条目需修正
  - **章节级**：「建议回审 X、Y 章」——该章结论受新证据实质影响
  - **整体级**：「建议旧卡回审」——版本变化动摇核心判断，或不回审档：「不必回审 + 理由」
